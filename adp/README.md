# Athlete Digital Passport (ADP): технический фундамент

ADP — следующая версия CloudPulse после конкурса (PRD v0.1). Эта папка — рабочая площадка для её кода. **До 06.11.2026 она ни к чему не подключена**: сайт её не собирает, в живую базу Supabase из неё ничего не запускается.

## Правила изоляции

| Что | Как обеспечено |
| --- | --- |
| Сайт не зависит от ADP | Корневой `tsconfig.json` исключает `adp`, `next build` сюда не смотрит. Ни одна страница сайта не импортирует файлы из `adp/`. |
| ADP не зависит от сайта | В `adp/tsconfig.json` нет алиаса `@/`: код ADP не может импортировать `lib/` или `components/` CloudPulse. Свой алиас: `@adp/*` → `adp/src/*`. |
| Живая база не трогается | Все таблицы лежат в отдельной схеме Postgres `adp`. SQL проверяется на тестовой базе, в рабочей Supabase не запускается до решения после конкурса. |
| Старая `profiles` не меняется | У ADP своя `adp.profiles`, привязанная к тем же аккаунтам (`auth.users`). |

## Правила продукта, которые код обязан соблюдать

1. **Матрица доступа = RLS.** Кто что видит, решает база, а не интерфейс.
2. **Без диагнозов.** Триаж только ищет красные флаги и блокирует нагрузку; вернуть полную нагрузку может только врач.
3. **Машина считает, человек решает.** Перенос контрольной система только предлагает, решает учитель.
4. **Без выдуманных чисел.** Нет данных — пишем «нет данных», а не 0.

## Как проверять

- Тесты TypeScript: `npm test` (Vitest сам находит `adp/**/*.test.ts` вместе с тестами сайта).
- Типы ADP: `npx tsc -p adp`.
- База и RLS: нужен локальный PostgreSQL 16 (не рабочая Supabase!):
  ```
  createdb adp_test
  psql -d adp_test -f adp/db/tests/000_supabase_stub.sql
  psql -d adp_test -f adp/db/migrations/001_init_adp_schema.sql
  psql -d adp_test -f adp/db/migrations/002_sport_profile.sql
  psql -d adp_test -f adp/db/tests/001_rls_matrix.sql
  psql -d adp_test -f adp/db/tests/002_sport_profile.sql
  ```
  Последние строки должны быть `ALL ADP RLS TESTS PASSED` и `ALL ADP SPORT PROFILE TESTS PASSED`. Тест работает в транзакции и всё откатывает.

## База данных (шаг 2)

12 таблиц в схеме `adp`: 5 из ТЗ (`profiles`, `academic_records`, `eligibility_statuses`, `reschedule_requests`, `safety_flags`) и 7 необходимых для матрицы доступа:

- связи `team_memberships`, `guardianships`, `teacher_assignments` — без них правило «тренер видит свою команду» не записать; создаёт их только сервер после подписанной формы согласия;
- `doctor_access` — доступ врача, который выдаёт сам спортсмен, максимум на 14 дней, отзывается в один тап;
- `check_ins` (ответы — видят только спортсмен и выбранный врач) и `daily_status` (цвет дня — для родителя и тренера);
- `grade_scales` — опорные точки перевода шкал (пример из PRD, ждёт утверждения школой).

Кто что пишет: чек-ины, цвет дня, флаги из чек-ина и статус допуска пишет только сервер (service_role) после движков на TypeScript. Клиент не может нарисовать себе зелёный день или спрятать красный флаг. Роли teacher / coach / doctor / scout нельзя выбрать самому — их выдаёт сервер.

Перед подключением к Supabase (после 06.11): добавить схему `adp` в Settings → API → Exposed schemas.

## API (шаг 5)

`api/openapi.yaml` (OpenAPI 3.1):

| Метод и путь | Кто вызывает | Что делает |
| --- | --- | --- |
| `POST /api/v1/check-in` | спортсмен | Чек-ин → TriageSafetyGuard; боль или красный флаг сразу дают красный и блок |
| `GET /api/v1/coach/roster-status` | тренер | Статус команды на день: цвет, блок, открытые флаги, цвет допуска. Без оценок и ответов |
| `POST /api/v1/academic/reschedule-request` | спортсмен | Запрос на перенос контрольной к своему учителю |
| `PATCH /api/v1/academic/reschedule-request/{id}` | адресованный учитель | Решение в одно нажатие; окончательное |

Кто вызывает, определяется только по токену Supabase: в теле запроса нет id вызывающего. Чужие данные отвечают 404, а не 403, чтобы нельзя было перебирать id. REST, а не gRPC: все клиенты — браузер/PWA, Vercel работает с HTTP/JSON.

## Движки и компоненты (шаги 3–4)

- **AcademicEngine** — `calculateEligibilityStatus(studentId)`. Красный, если хоть один предмет ниже проходного балла ИЛИ среднее ниже порога; жёлтый — в пределах запаса над линией; без подтверждённых школой оценок — «нет данных», а не зелёный. Для каждого проблемного предмета считает, какая минимальная оценка нужна на следующей работе. В базу сохраняет только цвет и код причины.
- **TriageSafetyGuard** — `processCheckIn(answers)`. Дерево из PRD 3.1: признак для 112 → удар по голове → боль → всё чисто. Любая боль сразу даёт красный и блок нагрузки, пропуск и запись к специалисту со сроком. Неснятый врачом красный флаг держит блок, даже если сегодня «всё хорошо». Сначала пишется блок, потом ответы: если запись сорвётся посередине, спортсмен уже заблокирован. Диагнозов нет — это проверяет отдельный тест.
- **PlayerRadarCard** — радар «ты сейчас против себя месяц назад». Сравнения с другими игроками нет вообще (нет даже такого параметра). В режиме `audience="shared"` ось «Восстановление» (данные о здоровье) не показывается. Нет данных — нет фигуры, только известные точки; ноль не рисуется. Каждая ось дублируется текстом со словом тренда — для экранного диктора и при дальтонизме.
- **TeacherRescheduleCard** — одобрение одним нажатием на предложенную дату; отказ в два нажатия, потому что он окончательный. Медицинская причина показывается без подробностей, даже если они пришли. Компоненты не ходят в базу сами: страница передаёт `onApprove` / `onReject`.
- Тексты на RU / LV / EN — `src/components/labels.ts`; компилятор проверяет, что во всех трёх языках есть все ключи.
- Все пороги и сроки — черновик из PRD, их утверждает врач клуба (`TRIAGE_RULES`) и соглашение школы с клубом (`DEFAULT_ELIGIBILITY_POLICY`).

## Sport-Aware AI Coach & Rehab Engine (в работе, с 30.09)

Модуль плана тренировки с учётом вида спорта, фазы сезона и «карты усталости». Правило то же: **движок решает (потолок нагрузки), ИИ объясняет и заполняет план только внутри потолка**. Никаких диагнозов и лечения (EU MDR): только стандартные мобильность, активация, изометрия, аэробная база.

- [x] Шаг 1 — типы и база (30.09).
  - `src/types/sportProfile.ts` (+12 тестов): вид спорта, фаза сезона, 18 зон силуэта (только мышцы — суставы не выбираются: «болит колено» идёт в триаж, а не в упражнения), серьёзность 1–5, осторожные зоны (поясница, шея, голени — направление к специалисту с 3/5), потолки движка `green / yellow / red / blocked`, микро-доза 12 мин, форма плана (только id упражнений из каталога, свободный текст не принимается).
  - `db/migrations/002_sport_profile.sql` + `db/tests/002_sport_profile.sql` (38 проверок): `adp.profiles.sport_type` (задаёт сам спортсмен, только роль student); **фаза сезона задаётся тренером на всю команду** — `adp.coach_seasons` (одна строка на тренера, время ставит база), `adp.season_phase_of(student)` — при нескольких тренерах действует последняя установленная; **карта усталости — часть чек-ина** `adp.check_ins.soreness_zones` (видят только спортсмен и выбранный врач, пишет только сервер, структуру проверяет `adp.valid_soreness_zones`). Списки в SQL и TS совпадают (проверено скриптом).
- [x] Шаг 2 — каталог упражнений (30.09): `src/services/rehabCatalog.ts` (+16 тестов). 54 стандартных упражнения ОФП на RU/LV/EN: прокат роллером, растяжка, мобильность, дыхание, активация, изометрия, эксцентрика, упражнения с собственным весом, лёгкая аэробика. У каждого — вид работы, зоны, виды спорта, минуты, усилие (RPE), дозировка, инвентарь. Три назначения: **relief** (мягкая работа на зону, которая сегодня забита: только мобильность/дыхание, RPE ≤ 2 — подходит даже под красный потолок), **prehab** (укрепление зон риска вида спорта — никогда на зону, которая сегодня забита), **general** (основа занятия). Проверки: у каждой зоны силуэта есть мягкая работа, у каждой зоны риска каждого вида спорта — прехаб; эксцентрика только в прехабе; в текстах нет слов «лечение / диагноз / травма / therapy / injury».
- [x] Шаг 3 — ИИ в рамках (30.09), +37 тестов:
  - `src/services/coachingLimits.ts` — **решает без ИИ**: берёт потолок движка и только ужесточает его — Return-to-Play (до допуска — только восстановление; после допуска 3 ступени за 14 дней), матч сегодня/завтра (только активация и мобильность), день после матча, фаза сезона (в сезоне дополнительное занятие ≤ 30 мин, межсезонье ≤ 45), экзаменационный шторм (микро-доза 12 мин без долгой аэробики и эксцентрики), карта усталости (забитая зона — только мягкая работа, слишком сильная/осторожная — только направление). На выходе — режим, минуты, RPE, разрешённые виды работы, причины и **список id упражнений, из которых ИИ может выбирать**.
  - `src/services/AIPromptBuilder.ts` — **Prompt Context Guard**: один замороженный JSON (вид спорта, фаза, числа движка, лимиты, карта, разрешённые упражнения с дозировкой) + системная инструкция для Claude (8 жёстких правил: только id из контекста, без диагнозов/лечения/питания, без новых чисел и процентов, ответ строго JSON). Имя и id спортсмена в запрос не попадают. Текст спортсмена — отдельно, очищенный, ≤ 300 символов, как данные, а не команды.
  - `src/services/planGuard.ts` — **проверка ответа**: неизвестное или неразрешённое упражнение, вид работы или RPE выше лимита, превышение минут, нагрузка забитой зоны, упражнения на зону «к специалисту», пропущенная мягкая работа, медицинские слова, проценты и числа, которых нет в контексте → ответ ИИ отклоняется, спортсмен получает **запасной план без ИИ** из того же контекста. Запасной план проходит проверку во всех 2160 комбинациях (вид спорта × фаза × потолок × шторм × RTP × карта). В день «blocked» ИИ даже не вызывается.
- [x] Шаг 4 — интеграционный тест (30.09): `src/services/coachScenario.integration.test.ts` (+11 тестов). Сценарий из ТЗ: **футболист, межсезонье, усталость в квадрицепсе 4/5, лимит движка YELLOW**. Проходит вся цепочка, как в продакшене: строка чек-ина `adp.check_ins.soreness_zones` → `fromSorenessRows` → `buildCoachingPrompt` → поддельная модель (без сети и ключа), которая видит **только текст промпта** → `coachPlan`. Пять вариантов модели: честная, «хулиганская» (Nordic, сплит-присед на забитый квадрицепс, 40 мин бега, RPE 8, «вылечит травму на 30%»), послушная prompt-injection от спортсмена, таймаут, ответ прозой. В каждом случае план спортсмена: один мягкий relief-блок на квадрицепс и больше ничего на него (ни приседа, ни выпада, ни step-up, ни стульчика), прехаб футбола (задняя поверхность / пах / сгибатели бедра / икры), ≤ 35 минут, RPE ≤ 5, без эксцентрики. Честная модель проходит на RU/LV/EN. Контроль: без усталости на зелёном предсезонье те же упражнения становятся доступны, на красном дне — только восстановление.
